# Layouts
## Overview

The Layouts guidelines provide foundational principles and specific recommendations for structuring the overall page organization within the design system. These guidelines aim to ensure consistency, usability, and optimal user experience across various page types and unique application areas, catering to different user tasks and information consumption patterns.

## Usage Guidelines

Layouts define the underlying structure and purpose of a page, guiding users through specific interactions or helping them process information efficiently. Selecting the appropriate layout depends on the primary goal and content of the page.

### Page Layout Types

These are standard layout patterns designed for common user interactions and information types.

*   **Lists**
    *   **Purpose:** To present collections of objects that users need to browse, inspect, and act upon.
    *   **Usage:** Ideal for directories, search results, or any page where the primary interaction involves reviewing multiple items.

*   **Grids**
    *   **Purpose:** To display visual information in an organized, scannable format, allowing users to quickly browse and target specific content.
    *   **Usage:** Suitable for galleries, dashboards with visual widgets, or areas where visual hierarchy is key.

*   **Workflows**
    *   **Purpose:** To guide users step-by-step through complex or multi-stage tasks, ensuring a clear path to completion.
    *   **Usage:** Essential for forms with many steps, setup processes, or any guided task flow.

*   **Settings**
    *   **Purpose:** To provide an interface for users to find and update application or system-level configurations.
    *   **Usage:** Used for pages dedicated to user preferences, account management, or system-wide configuration options.

*   **Profiles**
    *   **Purpose:** To display and allow editing of detailed information pertaining to a single object or entity.
    *   **Usage:** Applicable for user profiles, detailed views of a specific item, or entity management pages.

### Unique Application Areas

These layouts are tailored for specific, often complex, parts of the application, addressing distinct user needs and functionalities.

*   **Onboarding**
    *   **Purpose:** To guide new users through initial setup tasks and introduce them to core functionalities of the product.
    *   **Usage:** Employed for first-time user experiences, product tours, or initial configuration sequences.

*   **Dashboard**
    *   **Purpose:** To serve as a centralized hub for reporting, displaying key metrics, summaries, and quick access to important functions.
    *   **Usage:** Best for executive overviews, personal task summaries, or data visualization at a glance.

*   **Pipeline**
    *   **Purpose:** To manage and visualize sales processes or other sequential progression flows.
    *   **Usage:** Specifically designed for sales management areas where items move through distinct stages.
    *   **Status:** Not yet built.

*   **Proposal editor**
    *   **Purpose:** To provide a dedicated environment for creating, editing, and managing proposals.
    *   **Usage:** For specialized content creation interfaces, combining text, media, and structured data entry.

*   **Settings area**
    *   **Purpose:** To consolidate account and user-level settings, offering comprehensive configuration options.
    *   **Usage:** A broader scope for settings management, encompassing personal preferences, security, billing, and system-wide controls.

## Anatomy/Structure

The content describes the high-level purpose and use cases for different page structures rather than specific visual elements or their anatomy. Each layout type implies a distinct organizational schema optimized for its intended purpose (e.g., a "Lists" layout would prioritize clear item presentation, while a "Workflows" layout would emphasize progress indication).

## Variants/States

The various layout types listed under "Page Layouts" and "Unique Application Areas" can be considered variants, each optimized for a specific context or task. The "Pipeline" layout is explicitly noted as a "WIP" (Work In Progress) and "[Not yet built]", indicating a future state or planned variant.
